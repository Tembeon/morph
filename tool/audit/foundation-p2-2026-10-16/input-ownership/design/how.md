# Input ownership how findings

Base: `cfade8834496cc0cf580230b0e097e172ec27514`; read-only inspection, no tests, devices or source edits. SDK source: `/opt/homebrew/Caskroom/flutter/3.19.1/flutter/packages/flutter/lib/src/` (installed Flutter 3.47.2). Paths below are repository-relative unless prefixed SDK. These are implementation facts and design inferences, not new verified behavior.

## Overview

The prototype shares one complete `MorphMenuMotion` between a source and root popup. A unique lease controls writes, but lease ownership currently does not imply ownership of input. The session registers a binding-global pointer callback for its whole lifetime. It can therefore command the menu while another root route is current, and later command the source landing tail while that source's page is covered.

There are three separate boundaries: hit-test/binding ownership of a physical pointer; permission to translate an event into model commands; and lease ownership of motion sampling/painting. Route currentness should constrain the second, without disabling passive model evolution, route disposal or source handback. Escape, imperative Back and Router Back are also distinct paths; route installation alone does not reroute all three.

## Key Concepts

- `_MenuSession._pointer`: the single physical pointer ID accepted by the global handler. It is not the model's `_Pointer`, which carries origin, hold, scroll and selection semantics.
- `ProbeMenuLease`: prevents an obsolete clock from writing motion after transfer. It does not validate current route, hit-test path, window or device ownership.
- `activeRoute`: this session's presentation, including a logically popped route still painting its close. It need not equal the root Navigator's current route.
- `_DismissAttempt`: route-owned policy operation. It is invalidated on cover/uncover and lifetime changes. This protects permission, not arbitrary model action deadlines.
- Model timeline: hold, dwell, delayed activation, delayed close, physics and card work share it. `pointerCancel` and `close` have materially different cancellation behavior.
- Primary focus: keyboard dispatch begins here, then follows its focus ancestors; widget `Actions` lookup starts from the primary focus's BuildContext and walks widget ancestors.

## How It Works

### Pointer route and the covered menu

`ProbeMenuSourceState.build` installs a source `Listener` and `_MenuSession` additionally registers `pointerRouter.addGlobalRoute(handlePointer)` (menu_route_probe.dart:124–150,170–188). The source Listener invokes the session before pushing the hidden root popup. This deliberately occurs before Navigator's ancestor Listener records that down. Root `Navigator._afterNavigation` calls `_cancelActivePointers` (SDK widgets/navigator.dart:5161,5908–5922). A late push would cancel the held down; the early push avoids that particular cancellation.

After opening, global routing is the continuing input transport, including original hold move/up. `handlePointer` selects an ID, obtains the active route clock or source clock, stamps the genuine event, then calls `transfer.pointer(transfer.owner,...)` (menu_route_probe.dart:360–397). Transfer maps it to model pointerDown/Move/Up/Cancel at canonical time (menu_transfer_probe.dart:81–100). There is no isCurrent check at this entry. The hidden-closing guard only covers `closing && !revealed`; a covered revealed menu and a closing revealed menu still accept fresh downs, row input and outside input globally. A root cover's controls can therefore drive both their own UI and the underlying model. SDK hit-test barriers cannot constrain a binding-global callback.

A cover push cancels pointers known to that Navigator, but this is asynchronous: `GestureBinding.cancelPointer` queues a real `PointerCancelEvent` at the front, dispatched before the next event/end of microtask, not synchronously (SDK gestures/binding.dart:334–345). Legitimate cover cancellation must not depend on this being received first or on a held pointer existing. Do not synthesize `PointerCancelEvent` and feed it back through binding to solve model ownership. A direct model/session command can cancel the library's interaction without canceling a pointer belonging to the covering route or altering other recognizers' event histories. The actual SDK cancel must still be received and safely ignored once session ownership has ended.

The model's `pointerCancel(t)` first advances due work, then clears `_pointer`, relaxes and clears highlight/release if relevant (menu_motion.dart:2743–2752). It does not clear queued work; it returns early when the finger already lifted. `_select` schedules `_activate` and `_requestClose` independently (3107–3149); action closures have no generation guard. `_requestClose` consults admission, but `_activate` does not (3046–3104). Thus a valid up just before cover can leave an activation deadline that fires while covered, even though admission correctly vetoes closing the current overlay. A cancellation implemented as `pointerCancel(currentTime)` may itself run that deadline before cancelling. This is an independent failure path from accepting new covered-route input.

**Recommended boundary (design inference):** on loss of this presentation's input eligibility, synchronously relinquish session pointer identity and invalidate pending interaction work before any model advance that can execute it. Use a named model operation with an explicit semantic contract, not a binding event. Decide whether cover cancels the entire presentation (existing `close(t)` clears pointer and whole timeline before advancing at 2461–2469) or preserves a passive open menu (requires selective invalidation of user action/hold/dwell work while preserving physics/card scheduling). The whole-timeline option is broader and changes presentation behavior; it is not interchangeable with pointer cancellation. Protecting only the callback at delivery time prevents hidden activation but can still allow obsolete selection visuals/work to advance. Protecting only route close admission already demonstrably does not cover activation. If the activation callback itself pushes the cover, its current delivery has already committed; cancel subsequent pending interaction work, not the already-running callback.

Do not call Navigator.pop synchronously from didChangeNext just because coverage is detected: SDK history callbacks can be inside Navigator's locked history flush. Invalidate/cancel locally there and defer any navigation mutation outside that flush with identity/currentness checks. A queued follow-up must not accidentally pop the cover.

### Closing and source handback while a different route is current

`didPop` marks closing and starts model close, then `_sample` advances the lease until the model reaches progress <=0; `_session.land` transfers the *same* model to the source and resumes its clock (menu_route_probe.dart:264–288,660–708). No currentness is required for this passive finish, which is appropriate. A different route can be current during this interval, including the ordinary underlying home after logical pop or a later covering route. Adding `if (!isCurrent) return` to `_sample` would freeze precisely that legitimate close and prevent cleanup.

After handback `activeRoute=null`, although the source model may still have a landing tail and the source's root page may remain covered. The existing global handler accepts a fresh down on the button rect whenever no route/openPending exists; it does not know whether the source page is eligible. `syncInputPhase` can call `present()` from that new model opening, producing a ghost popup above the cover. Input eligibility therefore needs a source-side context/current-route check in addition to the route-side check, and for nested sources must include the root presentation context (the nested page remains locally current while its root parent is covered). A source-only `ModalRoute.of(sourceContext).isCurrent` check is insufficient in that nested case. Preserve passive landing samples and ignore fresh covered input.

### Escape with nested retained focus

WidgetsApp defaults map Escape to DismissIntent (SDK widgets/app.dart:1272,1321,1351). ShortcutManager handles it using `primaryFocus.context`, obtains the nearest action and invokes only if enabled (SDK widgets/shortcuts.dart:924–940). Every ModalRoute puts `_DismissModalAction` above its own focus scope; that action is enabled only if its route is barrierDismissible and calls `Navigator.of(itsContext).maybePop()` (SDK widgets/routes.dart:975–990,1197–1203).

Revealed popup focus therefore normally resolves its root route's action and pops the root popup. Existing test menu_route_probe_test.dart:431–485 tests Escape only after an editor popup has been revealed and a cover removed. It is not hidden nested focus evidence.

A hidden preparation returns requestFocus=false; existing source focus is deliberately retained (menu_route_probe.dart:614; menu_route_input_test.dart:232–268). If that focus is in a nested Navigator page, its nearest DismissIntent action belongs to the nested modal scope. It either refuses Escape (ordinary nondismissible PageRoute) or calls the nested Navigator, never the sibling root popup's action. An Actions widget inside hidden popup content cannot intercept a key whose primary focus is elsewhere; that content also intentionally does not exist yet. An Actions widget above the root Navigator is masked by the nested route's nearer action. `Actions.maybeFind` selects the nearest matching type before checking enabled, so a disabled nearer action does not automatically fall back to an outer override (SDK widgets/actions.dart:901–914).

**Can ordinary widgets solve it?** Yes with a deliberate source-page/host integration point: a DismissIntent action/shortcut wrapper that is below the nested modal action and above every retained focus candidate can direct dismissal to the live root preparation. This must include sibling editors and focus nodes outside the source button subtree. Merely wrapping the button is not general; a previously focused sibling or ancestor focus scope is outside that wrapper. Source-local Focus.onKeyEvent is similarly bounded by its focus ancestry. Changing focus to a hidden popup scope is another structural option, but violates the current retained-focus contract and affects editing, IME, traversal and accessibility. The source widget by itself cannot guarantee a standard Actions interception for arbitrary retained focus elsewhere in the page. Any host-integrated solution should remain an explicit integration requirement rather than claiming route-local magic.

A FocusManager early key handler can intercept before primary-focus ancestry, but is a global policy override, not a harmless implementation detail. SDK invokes *all* early handlers into a result list before combining results; one returning handled does not stop another handler from also mutating state (focus_manager.dart:2249–2275). Multiple sessions/menus therefore need exclusive ownership or precise eligibility arbitration, not independent handlers each claiming Escape. It can override an editor's more local Escape meaning. Register only for the exact hidden active operation and remove on reveal/cover/pop/dispose; accept only appropriate key-down (not repeat/up), match the active originating focus/view, and verify root route/session identity before consuming. KeyEvent has no viewId in this installed SDK; infer view from retained-focus context / explicit host scope, rather than assuming root-route isCurrent proves active-window ownership. FocusManager is shared by the WidgetsBinding and can see several view trees in one isolate. A per-session global handler without focus/view ownership risks dismissing a preparation in window A while handling a key focused in window B. These are costs and required tests; no early-handler implementation is recommended as already proven.

### Imperative Back versus Router Back

`rootNavigator.maybePop()` directly selects the root's last present entry. SDK awaits willPop then checks Navigator mounted, that the last entry is still identical, and current popDisposition before popping (navigator.dart:5582–5620). The existing hidden-preparation root Back test invokes this API directly (menu_route_lifecycle_test.dart:134–153); it does not send platform Back.

For ordinary WidgetsApp, platform didPopRoute delegates to its root Navigator.maybePop, irrespective of primary focus/nested current page (app.dart:1607–1620). For WidgetsApp.router the same method returns false; RootBackButtonDispatcher observes the binding and invokes RouterDelegate.popRoute (router.dart:1091–1112,805–809). ChildBackButtonDispatcher priority is explicit, with most recently prioritized children consulted first; a child that returns true prevents parent routing (router.dart:989–1059). Thus a prioritized nested router can consume Back before the root popup, unless the application's delegate/dispatch contract accounts for top-level pageless overlays. PopNavigatorRouterDelegateMixin specifically forwards popRoute to its keyed Navigator.maybePop and explicitly preserves pageless routes in *that* Navigator (router.dart:1597–1616). It does not promise a different root's pageless overlay beats an independently prioritized child router. Test actual binding Back and a real Router/dispatcher harness separately; do not infer either from direct root maybePop.

## Where Things Live

- `example/lib/proto/menu_route_probe.dart`: source Listener, binding-global input, session lease transfer, dismissal and root popup focus/lifetime.
- `example/lib/proto/menu_transfer_probe.dart`: model command ownership and canonical time translation.
- `lib/src/widgets/menu_motion.dart`: measured pointer semantics and delayed interaction callbacks; close clears timeline whereas pointerCancel does not.
- `example/test/proto/menu_route_input_test.dart`, `menu_route_lifecycle_test.dart`, `menu_route_probe_test.dart`: existing real input, hidden focus, root maybePop, nested hold and revealed Escape evidence.
- SDK `widgets/{navigator,routes,focus_manager,shortcuts,actions,app,router}.dart`, `gestures/binding.dart`: navigation cancellation, actual keyboard lookup and Back dispatch.

## Gotchas

- isCurrent is necessary for new root-menu input, not sufficient for source input in nested routes or for active-window ownership.
- No hit-test rule constrains a global pointer route. Also consider pointer view identity: this session currently compares only coordinates and pointer IDs, not the source FlutterView.
- When one covering route is removed and another remains above the menu, didPopNext must not by itself be treated as input eligibility; consult real currentness.
- Clearing session ID prevents new move/up commands but does not clear model-held state or already-lifted selection deadlines.
- Cancellation after an already-executed activation cannot undo user effects. State the chosen ordering at synchronous cover versus due deadline explicitly; never backdate cancellation.
- Passive physics/handback can legitimately continue while non-current. Input revocation and clock lease revocation are different operations.
- Global keyboard interception solves reachability by changing precedence. A bounded host Actions integration preserves ordinary precedence but requires an integration surface covering the retained focused subtree.
- Existing host tests do not establish native keyboard/IME, multiwindow, Router child-priority, or device behavior.
