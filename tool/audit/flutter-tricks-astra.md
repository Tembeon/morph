**Flutter mechanisms worth testing on weak devices — independent source audit, 2026-10-05**

The strongest additional opportunities are preserving small damage regions on Metal, using layer-property updates for appearance-only changes, warming actual pipeline configurations, and reducing texture upload/allocation overhead. Reduced precision and reduced resolution are experiments with visible failure modes, not free quality settings. Android Vulkan/GLES cannot be credited with Metal's partial-repaint savings in this revision.

This is source research, not a performance measurement. I read CLAUDE.md, the glass-renderer passport, perf-research-2026-10-05.md, perf-opinion-fable.md, and both unified-canvas opinions before preparing this list. Their already implemented grouping, plain-union, shadow, snapshot, uniform, and clock fixes are not proposed again. The current tree already has clock dozing (`lib/src/widgets/clock.dart:65`), an activity-indicator wake deadline (`lib/src/widgets/activity_indicator.dart:188`), and sample-identity field-upload reuse (`lib/src/glass/renderer/internal/flutter_gpu_geometry_renderer_native.dart:1024`). Earlier opinions describing those as missing are historical.

Only this report was written. No build, compiler experiment, test, device run, generated asset, or commit was made. Expected gains below mean avoided work, not measured milliseconds or a promise about A12–A14/Adreno/Mali performance.

**1. Update composited properties without repainting children.**

**3.47.2: yes. Gain: M–H UI in appearance/transform-only animation, little inherent GPU saving. Fidelity: low with exact invalidation, high if misclassified. Effort: M. Applies to** `lib/src/glass/renderer/rendering/liquid_glass_layer.dart:1183`, `lib/src/glass/renderer/internal/transform_tracking_repaint_boundary_mixin.dart:22`, `lib/src/widgets/glass.dart`, `lib/src/widgets/bar_items.dart`, and `lib/src/widgets/glass_button.dart`.

`RenderObject.markNeedsCompositedLayerUpdate` schedules `updateCompositedLayer` without child paint for an established repaint boundary. It falls back to paint if no boundary layer exists. The returned object must remain the same `OffsetLayer` instance/type, and the framework owns its offset (`F/src/rendering/object.dart:3107`, `:3381`). `RenderOpacity` is the concrete precedent (`F/src/rendering/proxy_box.dart:913`, `:941`). A plain `BackdropFilterLayer` cannot simply be returned from this hook: use an `OffsetLayer`-derived owner containing the filter/clip layers.

Morph already updates existing filter and clip handles in `_syncMaterialFilter`. Extend that path into a precise update classification: layout/shape, matte, material, optical uniforms, transform, clip, and foreground content. A tint/highlight change that affects only the final shader should replace the filter property and mark the owner for a composited-layer update; it need not record unchanged label/shadow pictures or rebuild the whole widget stack. This is the concrete Flutter mechanism behind the previous render-object-host proposal, not a second architecture proposal.

Important limitation: changing `FragmentShader` floats is not sufficient to update an already materialized filter. The Dart filter lazily retains its native filter (`E/lib/ui/painting.dart:4675`), and conversion copies uniform bytes for raster-thread consumption (`E/lib/ui/painting/fragment_shader.cc:97`). Keep the existing filter when inputs are equal; create a fresh filter when they change. The copy happens at native conversion, not necessarily at the Dart constructor call. Retaining the filter caches its description, not the filtered pixels.

**2. Retain EngineLayers; narrow the cost of `alwaysNeedsAddToScene`.**

**3.47.2: yes. Gain: M UI/scene construction with many resting surfaces; conditional raster diff saving. Fidelity: medium/high retained-motion risk. Effort: M. Applies to** `lib/src/glass/renderer/internal/transform_tracking_repaint_boundary_mixin.dart:120`, `lib/src/glass/renderer/rendering/liquid_glass_render_object.dart`, and `lib/src/glass/renderer/internal/retained_glass_clip.dart`.

Clean framework layers with an engine handle use `SceneBuilder.addRetained` (`F/src/rendering/layer.dart:696`). `alwaysNeedsAddToScene` disables that fast path, and a dirty descendant propagates dirtiness upward (`:407`, `:484`, `:1160`). It does **not** dirty every sibling, force layout, or itself schedule a new frame. The container's dirtiness traversal still visits children even when they ultimately remain clean (`:1160`); retaining a subtree does not eliminate this entire Dart traversal.

Morph's tracker has `alwaysNeedsAddToScene => true`, polls in `updateSubtreeNeedsAddToScene`, and flushes pending GPU submissions in `addToScene` (`.../transform_tracking_repaint_boundary_mixin.dart:137`, `:140`, `:159`). A useful experiment is to retain the pre-scene polling needed for arbitrary ancestor motion but mark actual effect layers dirty only on changes; move the submission guarantee into a single verified pre-scene owner before allowing trackers to stay clean. Removing the flag alone can skip the submission hook. Restricting polling solely to transform changes can miss opacity, clips, detach/reparent, or backdrop dependencies.

Engine retention is also not a promise of a free diff: `E/flow/layers/container_layer.cc:80` excludes retained subtrees containing readback or texture regions from its simple unchanged-subtree shortcut. Glass is precisely a readback-dependent case. Expect scene-build savings first; measure raster savings separately.

**3. Place RepaintBoundaries at independently changing content, not at every shape.**

**3.47.2: yes. Gain: M UI where repaint frequencies differ; zero guaranteed filter/GPU caching. Fidelity: low, except snapshot fallback interactions. Effort: S–M. Applies to** `lib/src/widgets/control_host.dart`, `lib/src/widgets/glass_liquid_native.dart`, `lib/src/glass/renderer/internal/content_snapshot.dart`, and `lib/src/widgets/bar_items.dart`.

The framework describes the benefit as separate display-list recording for child and surrounding tree (`F/src/rendering/proxy_box.dart:3461`). Thus one boundary around stable foreground content plus an independently updated glass owner can be more useful than one around everything. Preserve boundaries already supplied by renderer objects/opacity; additional nested boundaries may save no recording and increase layer work. Use repaint asymmetry, not widget count, as the criterion.

There is no general Impeller raster cache behind this: Metal, Vulkan and GLES surfaces return false from `EnableRasterCache` (`E/shell/gpu/gpu_surface_metal_impeller.mm:372`, `gpu_surface_vulkan_impeller.cc:311`, `gpu_surface_gl_impeller.cc:170`). Do not expect `CustomPaint.isComplex` or a boundary around stationary glass to memoize its blur while the background scrolls. Also check the content-snapshot supported layer types before adding compositing inside lens labels; an innocent boundary/clip arrangement can select the image fallback in `lib/src/glass/renderer/internal/content_snapshot.dart`.

**4. Exploit damage regions on iOS Metal; do not budget them on Android Impeller.**

**3.47.2: partial, platform-specific. Gain: potentially H GPU/energy for small animations on otherwise static pages; little for full-screen scrolling. Fidelity: low if bounds are correct. Effort: S investigation, M bounding changes. Applies to** `lib/src/glass/renderer/rendering/liquid_glass_layer.dart:1183`, `lib/src/glass/renderer/internal/ancestor_clip.dart`, `lib/src/widgets/scroll_edge_effect.dart`, and `lib/src/widgets/glass_body_shadow.dart`.

| Backend | Verified behavior |
|---|---|
| iOS Metal Impeller | Supported and enabled unless the host sets `FLTDisablePartialRepaint`. Constructor reads the Info.plist key (`E/shell/gpu/gpu_surface_metal_impeller.mm:34`); surface reports existing damage and `supports_partial_repaint = true` (`:206`). There is no package Dart switch to improve it. |
| Android Vulkan Impeller | Not enabled on the examined surface path. Both the ordinary swapchain return (`E/shell/gpu/gpu_surface_vulkan_impeller.cc:136`) and external-image return (`:277`) leave partial repaint at `FramebufferInfo`'s false default (`E/flow/surface_frame.h:39`). A working Dart enable switch or Android Vulkan damage path was **not found**. |
| Android GLES Impeller | Explicitly disabled: `E/shell/platform/android/android_surface_gl_impeller.cc:211`. Do not generalize the GL embedder or Skia implementation to Android Impeller. |

Metal partial repaint is not simply “draw only the changed widget.” It accumulates buffer damage, needs previous-buffer contents, and can be forced full when the external-view embedder is involved (`E/shell/common/rasterizer.cc:782`). Impeller rejects damage rectangles that are nearly full screen: width ratio **or** height ratio must be at most 0.7 after the full-buffer exclusion (`E/flow/compositor_context.cc:199`). This is a dimensional test, not a 70%-of-area test. It trades an additional resolve texture/final blit for reduced drawing (`:202`; `E/impeller/renderer/backend/metal/surface_mtl.mm:128`).

A BackdropFilter does **not** categorically turn partial repaint off. It contributes the cull rectangle as paint bounds and records a filter-input readback region (`E/flow/layers/backdrop_filter_layer.cc:25`). Damage touching either readback or output expands to include both (`E/flow/diff_context.cc:104`). An unbounded filter can therefore make the result effectively full-screen; separated top/bottom effects can produce a large union rectangle. A small clipped glass control can still leave useful damage savings.

Test a moving thumb, spinner, caret, and unrelated animation beside static glass on A12/A14 Metal. Compare damage rectangles and actual GPU work with full scrolling. This corrects the earlier blanket formulation that every on-screen glass filter necessarily incurs the same full reraster on every scheduled frame; partial repaint/culling can spare unaffected work on Metal.

**5. Bound the filter's output and its sampling support independently.**

**3.47.2: yes for clipping, no custom shader sampling-radius API found. Gain: M–H raster/GPU, plus item 4 on Metal. Fidelity: high if sampling support is cut. Effort: M. Applies to** `lib/src/glass/renderer/rendering/liquid_glass_layer.dart:1155`, `:1183`, `:1331`, `lib/src/widgets/glass_liquid_native.dart`, and `lib/src/widgets/scroll_edge_effect.dart`.

Impeller limits subpass coverage by current clip coverage and parent/render-target bounds (`E/impeller/display_list/canvas.cc:1695`, `:1740`). A tight rectangular clip limits filter work; a complicated silhouette with the same bounding rectangle is not evidence of a proportionally smaller intermediate texture. Keep disjoint, widely separated effect regions separate where the empty bounding area outweighs setup overhead; the unified-canvas audits already cover the larger batching decision.

`ImageFilter.shader` has **identity bounds mapping** at the display-list level: output bounds equal input bounds and requested input bounds equal output bounds (`E/display_list/effects/image_filters/dl_runtime_effect_image_filter.cc:17`, `:32`). Its constructor exposes only the shader, not a maximum displacement/input-outset parameter (`E/lib/ui/painting.dart:4461`). The engine binds sampler 0 and writes the input texture size into the first vec2 (`E/impeller/entity/contents/filters/runtime_effect_filter_contents.cc:128`). It does not infer morph's refraction reach from GLSL.

Consequently, do not shrink the clip to the visible silhouette blindly. Preserve the blur, displacement, dispersion, and shrink support represented by `backdropSamplingReach`; verify sampled pixels across all ancestor clips. A shader reading outside the engine's declared dependency region is also a damage-correctness risk, not just an edge artifact. Tightening an allocation bucket and tightening the true sampling region are different changes.

Another qualification: clipping final filtering does not prove an equivalently small backdrop capture. `FlipBackdrop` ends the current pass and obtains its target texture (`E/impeller/display_list/canvas.cc:2415`, `:2433`). Count capture/resolve traffic independently of filtered pixels. Do not multiply a presumed full-screen copy size by every filter as though that were measured external-memory traffic.

**6. Let Impeller downsample Gaussian blur; investigate the blur-to-runtime-filter bridge.**

**3.47.2: yes, automatic. Gain: already present; M conditional for avoiding extra bridge work. Fidelity: low for retention, high for replacing the kernel. Effort: S diagnosis, L engine-level alternative. Applies to** `lib/src/glass/renderer/rendering/liquid_glass_layer.dart:1162` and `lib/src/glass/renderer/shaders/liquid_glass_final_render_core.glsl`.

Impeller already chooses blur scale from sigma: unit scale through sigma 4, power-of-two downsampling, with a 1/16 floor and an extra quality guard near the 1/8 transition (`E/impeller/entity/contents/filters/gaussian_blur_filter_contents.cc:751`). The downsample arguments use the smaller scale selected for the axes (`:284`), and rendering has downsample plus separable blur stages (`:876`, `:904`, `:934`). Do not add another application downsample under the assumption Flutter does every Gaussian at full resolution.

The interesting remaining expense is that a runtime filter can re-rasterize its input snapshot to absorb a transform. The source specifically discusses a composed backdrop runtime effect outside an inner blur (`E/impeller/entity/contents/filters/runtime_effect_filter_contents.cc:57`, `:120`). Morph uses exactly that composition. Verify the extra intermediate on device; a cached geometry matte does not avoid it. The current API gives sampler 0 to the engine, so a package cannot simply substitute the internally downsampled blur texture or borrow the live scene target (`E/lib/gpu/lib/src/context.dart:49`). A custom blur over an explicitly owned background image is feasible, but general compositor-backdrop reuse would need a different API/engine design.

Keep measured sigma and sampling behavior. Fewer kernel taps, Kawase/pyramid approximations, or changing blur order are fidelity changes, not equivalent implementations proved by this audit.

**7. `ImageFilter.blur(bounds:)` is available, but is not a free bounds hint.**

**3.47.2: yes. Gain: unproven/conditional; not recommended as a blanket optimization. Fidelity: medium/high at boundaries. Effort: S experiment. Applies to** `lib/src/glass/renderer/rendering/liquid_glass_layer.dart:1169` and `lib/src/widgets/scroll_edge_effect.dart`.

This version adds a bounded mode that substitutes transparent samples outside the supplied rectangle, then renormalizes using effective alpha (`E/lib/ui/painting.dart:4347`, `:4361`). The native constructor passes the bounds into `DlBlurImageFilter` (`E/lib/ui/painting/image_filter.cc:72`); Impeller uses them in the blur and final unpremultiplication (`E/impeller/entity/contents/filters/gaussian_blur_filter_contents.cc:846`, `:939`). However, the display-list bounds calculation still expands by three sigma (`E/display_list/effects/image_filters/dl_blur_image_filter.cc:26`).

This is a possible tool for a specifically measured clipped-glass edge, not a reason to substitute the visible glass box for morph's current mirrored sampling. It changes which colors enter the blur. No source evidence establishes a general allocation/pass saving merely from providing this argument.

**8. Reduced-resolution geometry: split optical data quality from outline quality.**

**3.47.2: yes, application-controlled texture sizes. Gain: M–H GPU/memory when geometry is large and changes, low for cached small mattes. Fidelity: medium/high. Effort: M. Applies to** `lib/src/glass/renderer/rendering/liquid_glass_layer.dart:1425`, `lib/src/glass/renderer/internal/flutter_gpu_geometry_renderer_native.dart:260`, `lib/src/glass/renderer/shaders/gpu/geometry_field_fragment.glsl`, and `lib/src/glass/renderer/shaders/liquid_glass_final_render_core.glsl`.

Flutter GPU accepts caller-specified texture dimensions and defaults to one sample (`E/lib/gpu/lib/src/context.dart:177`). Morph currently derives matte dimensions from physical DPR, while the material map is already 8× smaller on each axis (`.../liquid_glass_layer.dart:1425`; `.../flutter_gpu_geometry_renderer_native.dart:247`, `:326`). A half-width/half-height matte contains one quarter as many texels; this arithmetic is not a 4× frame-speed claim, because capture, blur, final shading, and CPU fusion remain.

Most promising experiment: retain the authoritative full-quality CPU outline/clip and evaluate whether slowly varying optical normals/thickness can be sampled more coarsely. Keep rim coverage/AA and high-frequency contours at full quality or analytic evaluation. A uniformly low-resolution packed displacement/coverage matte is riskier: tiny highlights, thin necks, and moving edges can shimmer despite acceptable still images. Keep all distances in one defined physical/logical coordinate system; do not halve displacement or sigma accidentally with texture dimensions. Test fractional translations, anisotropic scale and every DPR used by weak-device targets.

Further reducing the already coarse material map is low priority. Contributor IDs and lookup rows are categorical/packed data, so resizing or linear filtering the complete texture is not equivalent to filtering a smooth color field. This is an optical-quality experiment and does not authorize changing the measured CPU trace grid or fusion law.

**9. Texture formats: RGBA16F is a plausible field-storage experiment; R8 is for genuinely scalar data.**

**3.47.2: yes as API formats, partial as portable per-usage capability. Gain: M memory/upload bandwidth, conditional GPU. Fidelity: medium for half fields, high for lossy repacking. Effort: M. Applies to** `lib/src/glass/renderer/internal/flutter_gpu_geometry_renderer_native.dart:1024`, `lib/src/glass/renderer/glass_field.dart`, and `lib/src/glass/renderer/shaders/gpu/geometry_field_fragment.glsl`.

The API exposes R8 UNorm, RGBA32F, RGBA16F and R32F (`E/lib/gpu/lib/src/formats.dart:69`, `:93`). Reported storage is respectively 1, 16, 8 and 4 bytes/texel (`:254`). The current sampled CPU field is RGBA32F, carrying distance, gradient components and half-thickness; its final matte is a different, packed representation. Do not conflate the two.

RGBA16F would halve this field's stored/uploaded bytes, not every glass texture or the scene buffer. It requires actual float-to-half packing: `Texture.overwrite` requires exactly the format's byte count (`E/lib/gpu/lib/src/texture.dart:199`), so passing the existing Float32List to a half texture is wrong. Conversion CPU cost may erase savings for small, frequently updated fields. Test normal angles, small distance differences, negative distances, and large thickness values; retaining higher precision for contour distance may be preferable to reducing all four channels together.

R8 can represent a coverage/mask or a carefully normalized scalar, not the current four-component field. Splitting channels adds samplers and possibly passes. RGBA8 sRGB is inappropriate for numeric distance/ID data; its documented color-space conversion differs from UNorm (`E/lib/gpu/lib/src/formats.dart:76`).

Critical weak-Android caveat: `GpuContext.supportsTextureFormat` currently returns true for **all known uncompressed formats regardless of usage** (`E/lib/gpu/context.cc:174`; Dart warning at `E/lib/gpu/lib/src/context.dart:100`). It cannot certify RGBA32F/16F filtering or renderability. Qualify the exact allocation/upload/sample/render combination on real GLES devices. A tiny complete smoke render is better evidence than the getter; catching allocation failure alone is insufficient.

**10. Shader `mediump`/`half`: distinguish compiler routing, numeric storage and executed arithmetic.**

**3.47.2: partial. Gain: L–M, potentially useful on arithmetic/register-bound weak GPUs; unmeasured and possibly zero. Fidelity: high for coordinates/codec, lower for bounded color terms. Effort: M plus backend inspection. Applies to** `lib/src/glass/renderer/shaders/liquid_glass_final_render_core.glsl:7`, `lib/src/glass/renderer/shaders/gpu/geometry_fragment.glsl:11`, `geometry_field_fragment.glsl:13`, and `displacement_encoding.glsl`.

Verified compiler path for both user runtime effects and Flutter GPU shaders:

| Target | What the pinned source proves; what it does not |
|---|---|
| Runtime `.frag` | GLSL enters shaderc as GLSL 460 core (`E/impeller/compiler/compiler.cc:423`). Runtime Metal/GLES use the OpenGL SPIR-V environment (`:477`); runtime Vulkan uses Vulkan 1.1/SPIR-V 1.3 and relaxed Vulkan rules (`:462`). These environment settings are not a promise of half arithmetic. |
| Metal | The compiler delegates to SPIRV-Cross `CompilerMSL`, with the options shown at `E/impeller/compiler/compiler.cc:128`. There is no explicit mediump-to-half transformation in this wrapper. The exact lowering of every `RelaxedPrecision` expression to MSL float/half is **not found/verified** because the SPIRV-Cross implementation is not in this shallow checkout. Do not claim that changing `precision highp float` to `mediump` guarantees half ALU on A12. |
| Vulkan | The shipped shader code is SPIR-V, recompiled without debug information, not the generated GLSL string (`E/impeller/compiler/compiler.cc:590`). The reflector recognizes `DecorationRelaxedPrecision` (`E/impeller/compiler/reflector.cc:751`), but this is not proof of 16-bit instructions, a Float16 device feature, or lower register use. Exact qualifier emission by the missing frontend and device-driver lowering are **not verified**. |
| GLES | SPIRV-Cross emits GLSL ES with the selected version (`E/impeller/compiler/compiler.cc:235`); runtime GLES3 is promoted to at least ES 300. Exact emitted precision qualifiers for a candidate shader require inspecting compiled output; the missing SPIRV-Cross implementation means a universal preservation/lowering claim is **not verified here**. |
| Explicit half in Flutter GPU bundles | Bundles compile separate Metal iOS, desktop, GLES and Vulkan variants, with platform macros (`E/impeller/compiler/shader_bundle.cc:90`, `:199`). Impeller's own `types.glsl` enables explicit float16 extensions but aliases `float16_t`/`f16vec*` back to float/vec outside `IMPELLER_TARGET_METAL_IOS` (`E/impeller/compiler/shader_lib/impeller/types.glsl:8`). A half-type fixture exists (`E/impeller/fixtures/half.frag:5`). This supports a Metal-specific investigation, not a portable half-shader guarantee. |

`--use-half-textures` concerns Metal texture semantics, not a universal “make shader half precision” switch (`E/impeller/compiler/source_options.h:33`; `compiler.cc:448`). Likewise, selecting RGBA16F storage does not establish that shader arithmetic runs at 16 bits. Runtime shader scalar uniforms use Float32List storage (`E/lib/ui/painting.dart:5991`, `:6058`); avoid changing their layout or shared GPU uniform-block ABI as part of a local arithmetic experiment.

Recommended candidate: keep screen/texture coordinates, affine subtraction, signed distance near zero, refraction, and packed matte encode/decode high precision; try reduced precision only on bounded tint/highlight/intermediate color calculations. Morph already documents visible large-layer GLES shimmer from mediump coordinate subtraction (`.../liquid_glass_final_render_core.glsl:7`). Before any adoption, inspect emitted MSL/GLSL/SPIR-V for the actual build, then compare GPU time and films. No promise of a gain from qualifiers alone is justified by the sources available here.

**11. Cache final glass output only with an explicit, complete backdrop revision.**

**3.47.2: partial/manual; no automatic Impeller glass-output cache found. Gain: H for static backdrop+glass while unrelated content animates, zero during relevant scrolling. Fidelity: high invalidation risk. Effort: L. Applies to** `lib/src/widgets/glass.dart`, `lib/src/widgets/glass_liquid_native.dart`, `lib/src/glass/renderer/rendering/liquid_glass_layer.dart`, and `lib/src/glass/renderer/internal/content_snapshot.dart`.

No general raster cache is enabled on these Impeller surfaces (item 3). Backdrop sharing in `Canvas::SaveLayer` caches inputs for multiple uses in the **current scene**, not a cross-frame result tied to arbitrary background changes (`E/impeller/display_list/canvas.cc:1801`). Final-output caching is therefore a package/application feature, not an EngineLayer setting.

A viable restricted design is an explicit owner that knows the complete background plane and publishes a revision. Cache only when background, glass shape/material/optics, relevant transforms, clip, DPR, color space and sampling footprint are unchanged. Then draw a retained image of the complete effect region and invalidate before the next changed frame. Video/external textures and native views require explicit invalidation/support; widget rebuild absence is not proof of unchanged pixels. Moving glass over a static background usually invalidates its sampled result too.

`OffsetLayer.toImage` builds a scene from that layer and its descendants (`F/src/rendering/layer.dart:1546`); wrapping only the BackdropFilter cannot capture preceding siblings as if they were inside that subtree. `Texture.fromImage` wraps an already GPU-backed image without a pixel copy, but does not obtain the current framebuffer; synchronous snapshot images may not yet have a compatible texture (`E/lib/gpu/lib/src/texture.dart:89`). Flutter GPU explicitly cannot render directly into the framework's onscreen target (`E/lib/gpu/lib/src/context.dart:49`). Thus a general drop-in glass freeze based on `RepaintBoundary.toImage` is not established. Start only with an explicit static background/effect container, and compare against Metal's existing damage avoidance before paying for another image cache.

**12. Warm real pipeline configurations, not merely asset handles.**

**3.47.2: yes, partially automatic; no public all-variants-complete warm-up API found. Gain: H first-use latency, no steady-state gain. Fidelity: low; startup/memory/energy cost. Effort: M. Applies to** `lib/src/widgets/glass_liquid_native.dart:20`, `lib/src/widgets/glass_renderer.dart` (`precache`), and `lib/src/glass/renderer/internal/flutter_gpu_geometry_renderer_native.dart:1065`.

`FragmentProgram` asset initialization already posts a raster task to bootstrap a variant without waiting (`E/lib/ui/painting/fragment_program.cc:206`). `BootstrapShader` selects a default color format and requests asynchronous pipeline creation (`E/impeller/entity/contents/runtime_effect_contents.cc:149`). Actual rendering can request a different cached option set and synchronously resolve it (`:358`, `:257`). Therefore awaiting morph's existing `precache()` does not prove all glass filter/blur/attachment combinations are ready.

Flutter GPU `createRenderPipeline` constructs a shader/vertex-descriptor wrapper (`E/lib/gpu/render_pipeline.cc:27`). The concrete pipeline is obtained from the render pass with sample count, color formats and depth/stencil descriptors (`E/lib/gpu/render_pass.cc:108`, `:149`). On a new GLES pipeline the code explicitly waits on raster-thread creation and warns that this can stall UI (`:154`). Vulkan also resolves the requested pipeline through `GetPipeline(...).Get()` (`:179`); its library creates missing pipeline objects (`E/impeller/renderer/backend/vulkan/pipeline_library_vk.cc:156`) and ultimately invokes the driver (`pipeline_cache_vk.cc:78`). Precompiled shader source/IR does not remove all driver pipeline work.

Concrete warm-up: use tiny **nonempty, actually submitted** draws of analytic geometry, field geometry, tint-only and mixed-material GPU variants; use representative runtime filters with/without inner blur and the attachment/blend/sample configurations actually used by the scene. Warm only likely first-use variants, before the first interaction. A completely clipped-away filter can be skipped (`E/impeller/display_list/canvas.cc:1718`, `:1752`), so the earlier “clipped-away warm-up widget” suggestion is not reliable. Offscreen and onscreen targets may select different pipeline descriptors; match them or explicitly accept incomplete coverage. Do not warm every possible permutation or create a new shader variant for every control.

Vulkan has a persistent pipeline cache: it loads existing data and retries with an empty cache if rejected (`E/impeller/renderer/backend/vulkan/pipeline_cache_vk.cc:30`); dirty cache persistence is checked every 50 acquired surface frames (`pipeline_library_vk.cc:279`). This can help repeat launches, but a short warm-up followed immediately by exit need not persist new entries. Test cold install/cache, second launch, and first appearance of each variant separately. Do not add idle frames merely to reach the persistence interval.

**13. Batch texture uploads; avoid `Texture.overwrite` per region.**

**3.47.2: yes. Gain: M CPU/driver/upload overhead for several changing fields or an atlas; low for one tiny field. Fidelity: low with correct ordering/lifetimes. Effort: M. Applies to** `lib/src/glass/renderer/internal/flutter_gpu_geometry_renderer_native.dart:1024` and its deferred-submission machinery at `:488`.

This is more concrete than the earlier generic “keep buffers” recommendation. `Texture.overwrite` allocates a staging buffer with a copy, creates a command buffer and blit pass, and submits it (`E/lib/gpu/texture.cc:61`, `:91`). GLES posts that work to the raster thread (`:119`). Host-visible texture allocation therefore does not make this Dart operation a zero-copy write.

The current API instead offers `CommandBuffer.copyBufferToTexture` with a rectangular `TextureRegion`; contiguous copies can share one backend blit pass (`E/lib/gpu/lib/src/command_buffer.dart:134`; native coalescing at `E/lib/gpu/command_buffer.cc:49`). Pack changed fields into reusable staging BufferViews, copy only used regions of capacity-bucketed textures, submit before geometry reads them, then issue the existing geometry passes. This avoids the whole-mip-size restriction of `overwrite` (`E/lib/gpu/lib/src/texture.dart:209`) and makes bucketed field capacity practical without uploading undefined padding.

Keep unchanged samples resident as today. A staging-ring entry is reusable after its last GPU **consumer**, not merely after the Dart producer function returns. The command buffer's completion callback is available (`E/lib/gpu/lib/src/command_buffer.dart:240`; UI dispatch at `E/lib/gpu/command_buffer.cc:230`), but completion of the field-writing pass does not establish completion of a later compositor sampling pass. Preserve morph's established lifetime constraints; do not shrink its texture rings on the strength of the producer callback alone.

**14. Persistent textures and dirty subrects, not reusable render passes.**

**3.47.2: yes for retained resources/load-preserve/scissor; no replayable command-buffer API found. Gain: M–H only for mostly unchanged large targets. Fidelity: medium/high stale-region risk. Effort: M–L. Applies to** `lib/src/glass/renderer/internal/flutter_gpu_geometry_renderer_native.dart:855` and any future bounded geometry atlas.

Textures can stay allocated and become `ui.Image` wrappers (`E/lib/gpu/lib/src/texture.dart:248`). `ColorAttachment` exposes load/store actions (`E/lib/gpu/lib/src/render_pass.dart:9`); `LoadAction.load` preserves content (`formats.dart:420`), and `setScissor` bounds draws (`render_pass.dart:607`). This permits incremental updates in an application-owned target. Reuse pipeline/texture/descriptor data, but record fresh work: Dart rejects submitting a command buffer twice (`command_buffer.dart:240`).

Morph currently uses `dontCare` because every pixel of the used subrect is rewritten (`.../flutter_gpu_geometry_renderer_native.dart:309`, `:855`). Changing only the scissor would leave stale/undefined pixels. An incremental atlas must clear old coverage as shapes move, redraw exposed contributors, include SDF/AA support, and keep unchanged tiles correct in every rotated texture version. Load-preserve adds work; for today's small full-coverage quads the existing discard/full-write can be better.

Do not combine separate render passes into one command buffer as a routine optimization in this pin. Flutter GPU begins the native pass at creation (`E/lib/gpu/render_pass.cc:77`), Metal creates an encoder immediately and ends it at encoding (`E/impeller/renderer/backend/metal/render_pass_mtl.mm:143`, `:188`), and submission encodes the registered passes (`E/lib/gpu/command_buffer.cc:28`, `:122`). This supports the repository's nested-encoder warning at `.../flutter_gpu_geometry_renderer_native.dart:488`. Multiple draws in **one** pass are a different and useful mechanism; multiple simultaneously created native passes are not a safe shortcut.

**15. Instanced bounded quads can replace all-shapes-per-pixel work.**

**3.47.2: yes; GLES acceleration partial. Gain: M–H for many independent primitives, low for current single quad/small-N layers. Fidelity: medium/high overlap semantics. Effort: L. Applies to** `lib/src/glass/renderer/shaders/gpu/geometry_vertex.glsl`, `geometry_fragment.glsl`, `material_gradient_fragment.glsl`, and `lib/src/glass/renderer/internal/flutter_gpu_geometry_renderer_native.dart`.

The public draw API supports `instanceCount` and per-instance vertex buffers (`E/lib/gpu/lib/src/render_pass.dart:631`, `:648`; explicit vertex-layout validation in `E/lib/gpu/render_pipeline.cc:85`). One quad per bounded primitive can restrict fragment execution spatially, with descriptors supplied as instance data. This is useful in a future compact container/atlas; “instancing is irrelevant because today's pass is one quad” does not rule out that redesign.

But GLES uses hardware instanced entry points only when available; otherwise it loops over instances and rebinds attributes (`E/impeller/renderer/backend/gles/render_pass_gles.cc:539`, `:592`). On the weakest fallback devices one Dart draw is not necessarily one hardware draw. Also, overwriting or alpha-blending overlapping quads does not implement nearest SDF selection, normal-modulated fusion, or the menu's Gaussian law. Preserve ordered ownership and fusion separately. This does not expose the final scene backdrop to Flutter GPU.

**16. Stencil/scissor and transient attachments: useful locally, no borrowed engine mask.**

**3.47.2: yes for owned passes. Gain: M conditional GPU; may regress small shapes. Fidelity: medium AA/coverage risk. Effort: M–L. Applies to** `lib/src/glass/renderer/internal/flutter_gpu_geometry_renderer_native.dart` and `lib/src/glass/renderer/shaders/gpu/geometry_fragment.glsl`.

Flutter GPU exposes stencil reference/configuration and scissor (`E/lib/gpu/lib/src/render_pass.dart:577`, `:586`, `:607`). RenderTarget owns its depth/stencil attachment (`:78`). A pre-mask can reject empty regions before a costly geometry/material pass; a rectangle scissor is cheaper when it describes the region adequately. A mask costs its own draw, attachment storage and potentially a resolve. It contains coverage, not optical distance/normal/thickness.

No API to attach the compositor's existing stencil to a Flutter GPU pass was found. A mask in an owned target will not automatically stencil the later `ImageFilter.shader`; that needs its own clip or sampled mask. Device-transient storage cannot be sampled as a normal texture (`E/lib/gpu/lib/src/render_pass.dart:492`), and transient depth/stencil cannot be loaded from a previous pass (`:110`). Use transient attachments only for genuinely pass-local masks/MSAA intermediates, not retained geometry textures.

**17. MSAA: keep data passes single-sampled; do not claim an app-wide off switch.**

**3.47.2: yes for custom targets, device-dependent; no package control of the scene's global sample count found. Gain: L now because morph already uses the single-sample default; M prevention of a regression. Fidelity: medium if geometric edge AA changes. Effort: S. Applies to** `lib/src/glass/renderer/internal/flutter_gpu_geometry_renderer_native.dart:855` and future mask/atlas passes.

Texture creation defaults to `sampleCount = 1` (`E/lib/gpu/lib/src/context.dart:177`). Offscreen MSAA support is queryable and absent on some GLES-only devices (`:49`). Resolve textures must match size/format and be single-sampled; a transient resolve destination is forbidden (`E/lib/gpu/lib/src/render_pass.dart:40`). A sample count also participates in pipeline selection (`E/lib/gpu/render_pass.cc:111`).

The matte/field is numerical data shaded by a full rectangle, not conventional triangle silhouettes needing an MSAA edge resolve. Retain one sample and the shader's measured coverage behavior. If a future instanced/stencil path introduces geometric edges, compare its AA explicitly before reducing samples. Do not multiply the current matte budget by four under an assumption that Flutter's onscreen MSAA also applies to every Flutter GPU texture.

**18. Move field evaluation to GPU only if it removes an actual CPU dependency.**

**3.47.2: partial — raster field generation yes; public Flutter GPU compute/SSBO/atomic dispatch not found. Gain: potentially H UI for expensive changing fusion, possibly negative GPU/energy. Fidelity: high. Effort: L. Applies to** `lib/src/widgets/menu_fusion.dart:88`, `lib/src/widgets/glass_outline.dart`, `lib/src/liquid_field.dart`, `lib/src/glass/renderer/glass_field.dart`, and `lib/src/glass/renderer/shaders/gpu/geometry_field_fragment.glsl`.

Fullscreen/bounded fragment passes can evaluate fields and separable kernels into owned textures using the existing render API. The exposed Flutter GPU `ShaderStage` enum contains vertex and fragment only (`E/lib/gpu/lib/src/formats.dart:449`); the context/command-buffer APIs examined expose no compute dispatch. Impeller's internal compute classes and compiler support do not make them public Dart capabilities.

The hard part is the CPU `Path` required by the current outline contract, shadows, clips and non-liquid tiers. Moving distance samples to a GPU texture while still tracing the same path on CPU duplicates work. Moving marching squares to GPU and reading it back each frame introduces an asynchronous dependency; texture-to-buffer copy exists (`E/lib/gpu/lib/src/command_buffer.dart:172`), but its existence does not make same-frame readback cheap or remove the CPU path requirement.

A sensible isolated experiment is GPU optical-field generation with the authoritative outline unchanged, first measuring whether the field-only part is large enough to matter. The passport already says that part was only 10–16% on the measured menu (`tool/ios_reference/spec/glass-renderer.md:395`), so the A18 result does not justify a rewrite by itself. Full GPU fusion needs a deliberate new outline/shadow/clip representation while preserving the measured law. Approximate metaballs are outside this proposal. Never accept a previous-frame neck just to avoid synchronization.

**19. Isolates help preparable numeric work, not automatically live SDF deadlines.**

**3.47.2: yes for numeric work; partial for this rendering path. Gain: M–H UI if enough work can be moved ahead, uncertain total CPU/battery. Fidelity: high if results lag current input. Effort: M–L. Applies to** `lib/src/widgets/menu_fusion.dart`, `lib/src/widgets/glass_outline.dart`, and `lib/src/liquid_field.dart`.

Native `compute` delegates to `Isolate.run` (`F/src/foundation/_isolates_io.dart:14`). TransferableTypedData takes linear time to create but constant time to send and has single-use materialization (`D/isolate/isolate.dart:1170`). Native-resource wrappers are not sendable (`:989`); canvas/image-filter/picture-recorder operations enforce root-isolate UI access (`E/lib/ui/ui_dart_state.cc:100`; `E/lib/ui/painting/canvas.cc:29`, `image_filter.cc:24`, `picture_recorder.cc:19`). Do not ship RenderObjects, GPU contexts/textures, or a canvas pipeline through the worker.

For genuinely large jobs, use one persistent worker with packed shape/time/revision input and numeric output buffers; reconstruct root-isolate UI objects after receiving the matching revision. Precompute invariant kernels, static complex shapes, or work known before an interaction. `compute` per 120 Hz tick is not established as a win. An interruptible spring's current geometry is not generally known a frame ahead; waiting for a worker still consumes the same deadline and displaying an old result changes motion. Bounded queueing and superseded-result rejection avoid backlog, but do not solve that fidelity constraint. Test throughput and response latency on weak multicore devices; another active core is not an idle-battery optimization.

**20. Dart VM pragmas: small, measured candidates; unsafe variants are unverified here.**

**3.47.2: partial verification. Gain: L, occasionally M in proven hot numeric loops. Fidelity: low for ordinary inlining, unacceptable unchecked-memory risk without proof. Effort: S trial, M validation. Applies to** `lib/src/widgets/menu_fusion.dart:351`, `lib/src/liquid_field.dart:439`, and numeric helpers in `lib/src/widgets/glass_outline.dart`.

`vm:prefer-inline` is used by this exact framework (`F/src/foundation/_isolates_io.dart:14`) and installed VM library (`D/_internal/vm/lib/typed_data_patch.dart:2218`). This establishes an existing toolchain hint, not guaranteed inlining or a speedup. Apply only to small repeatedly called arithmetic helpers identified in release/AOT profiles; compare code-size and instruction-cache effects. Large SDF samplers/blur loops are poor blanket-inline candidates. Keep loop lengths/types obvious and scratch arrays stable before trying directives.

The installed Dart VM library also uses `vm:unsafe:no-bounds-checks` and `vm:unsafe:no-interrupts` (`D/_internal/vm/lib/convert_patch.dart:825`). Thus the names are not invented, but their exact compiler handling, application-code restrictions and AOT scope were **not found in the supplied sources**. The VM compiler dependency is absent, so this report does not certify them for morph or claim a percentage gain. Do not infer safety from SDK-internal use. Any future bounds-check-elimination trial needs the pinned compiler source, generated-code evidence that redundant checks actually remain, and a proof for every index/length/overflow path. Suppressing interrupts is especially inconsistent with a latency-sensitive UI unless carefully bounded; no recommendation to use it here.

SIMD/FFI rewrites are likewise not credited with a gain without AOT evidence. Float32 storage can change the current Float64 accumulation and fusion contour; reducing allocation does not authorize changing numeric precision in the measured law.

**21. Frame scheduling: retain the existing sleeping clock, measure actual cadence.**

**3.47.2: yes for demand-driven scheduling/TickerMode; partial for refresh-rate control. Gain: H energy when a frame is avoided, no new win from already completed sleep fixes. Fidelity: high if active motion is throttled. Effort: S checks, M host integration. Applies to** `lib/src/widgets/clock.dart:65`, `lib/src/widgets/activity_indicator.dart:188`, `lib/src/widgets/glass_tier.dart:276`, and `lib/src/widgets/flex_integrator.dart`.

An active, unmuted ticker schedules frame callbacks (`F/src/scheduler/ticker.dart:270`, `:289`); muting cancels scheduled ticking (`:119`). Scheduler frame requests are coalesced (`F/src/scheduler/binding.dart:946`). iOS display links start paused, resume on demand and can pause after vsync (`E/shell/platform/darwin/ios/framework/Source/VSyncClient.swift:65`, `:112`, `:199`). Android's waiter posts a Choreographer callback when asked (`E/shell/platform/android/io/flutter/view/VsyncWaiter.java:118`). A persistent-frame callback registration is not by itself a request for continuous frames.

The remaining work is to verify no extra frames while settled, finger-held-but-static, covered/offstage, or backgrounded; also audit timer wakeups, not just paints. Morph already has dozing, so do not add a second clock or lower the measured flex/sub-clock frequency. TickerMode is useful for genuinely inactive subtrees, but timers and non-ticker scheduling need their own lifecycle policy. Stop offscreen work rather than running a ticker and merely skipping paint.

For iOS high-refresh pacing, the engine reads `CADisableMinimumFrameDurationOnPhone` (`DisplayLinkManager.swift:28`) and sets a preferred range when variable refresh is enabled (`VSyncClient.swift:89`). The same source warns that its reported display rate is instrumentation, whereas scheduling uses per-frame duration (`DisplayLinkManager.swift:43`). Treat 120 Hz availability, reported refresh rate and observed presentation cadence as separate quantities. The old iPhones named in the request do not become faster by being assigned an 8.33 ms budget; use their actual display/cadence and preserve the package's measured motion mapping.

Android refresh changes are observed and forwarded to the engine (`E/shell/platform/android/io/flutter/view/VsyncWaiter.java:34`, `:70`). These calls update timing knowledge; they do not request a higher display mode. A public Dart display-mode setter or host `Surface.setFrameRate` call in this Android source path was **not found**. Any app-level refresh-mode integration needs separate native validation. Do not secretly force 60 Hz to make frame percentiles look better, and do not infer a weak device's GPU speed from its advertised 90/120 Hz panel.

**22. Choose an initial tier from capability and workload evidence, not a made-up device score.**

**3.47.2: partial. Gain: H avoidance of a bad first interaction; no inherent speedup. Fidelity: tier changes are visible. Effort: M. Applies to** `lib/src/widgets/glass_tier.dart:248`, `lib/src/glass/renderer/internal/liquid_capability.dart`, and `lib/src/widgets/glass_liquid_native.dart:20`.

Available signals include display physical size/DPR/rate (`E/lib/ui/window.dart:9`), shader-filter support (`E/lib/ui/painting.dart:4483`), successful GPU context initialization, offscreen-MSAA/mipmap/compression capabilities (`E/lib/gpu/lib/src/context.dart:22`), and CPU count (`D/io/platform.dart:63`). GPU initialization requires Impeller and the host's Flutter GPU enable setting; the exact Info.plist/manifest names are in `E/lib/gpu/context.cc:46`. Android's dynamic Impeller selection can fall back from Vulkan to **Impeller GLES** (`E/shell/platform/android/android_context_dynamic_impeller.cc:185`). Skia GLES is a distinct case: ImageFilter.shader support is false there by the Impeller gate.

No public Flutter GPU vendor/model/driver identifier, compute-unit count, memory-bandwidth score, per-format float capability query, thermal-state getter, or GPU-duration result was found in the examined Dart context/render APIs. CPU count alone is not an ordering of mobile performance. The current capability loader creates resources and loads shader assets but does not execute all usage combinations (`lib/src/widgets/glass_liquid_native.dart:20`), so add a small representative render before promoting an unqualified backend.

Proposed policy input, not a verified existing API: let the host supply a device/driver class and thermal/power constraints through an optional interface; retain explicit tier override and FrameTiming governor. Start from a conservative **measured** profile keyed to actual backend/driver and physical effect area, then adjust with observed timing. Device model/RAM/thermal native APIs and a validated A12/Android allowlist are **not established by this checkout**. Do not invent one here. Keep capability failure separate from performance demotion, and do not repeat the already rejected assumption that frosted is always cheaper than liquid.

**23. Release spare GPU capacity on memory pressure without waking idle frames.**

**3.47.2: yes for notification; resource reclamation timing only partial. Gain: M memory resilience, indirect latency benefit on low-memory devices. Fidelity: low if only unused capacity is dropped. Effort: S–M. Applies to** `lib/src/glass/renderer/internal/flutter_gpu_geometry_renderer_native.dart:586`, `:602`, `:1020`, and `lib/src/widgets/glass_tier.dart`.

The renderer ages spare/released textures in frame counts and trims from a persistent-frame callback. Once the app becomes idle, those counts stop advancing. That is good for battery but means “120 idle frames” is not a wall-clock expiry. Flutter exposes `WidgetsBindingObserver.didHaveMemoryPressure` (`F/src/widgets/binding.dart:400`, dispatch at `:1376`). Use it to discard unreferenced pool entries and optional cached outputs, with explicit byte budgets rather than texture counts alone. A few very large textures can dominate a count-limited pool.

Do not schedule frames solely to age the pool. Do not drop an image still referenced by a retained filter, or reuse its backing texture while an older scene samples it. The examined GPU Texture Dart API has no explicit public dispose operation (`E/lib/gpu/lib/src/texture.dart:135` through `:315`); dropping references does not establish immediate physical-memory return. Measure resident/peak memory after pressure and after repeated menu growth/shrink, rather than claiming deterministic freeing from a counter decrement.

**24. A tempting VM latency-mode API has a version-specific caveat.**

**3.47.2: partial. Gain: unknown/conditional GC-tail improvement; possible memory/energy regression. Fidelity: low, app-wide policy risk. Effort: S source investigation, M host coordination. Applies to** `lib/src/controller.dart`, `lib/src/widgets/clock.dart`, and allocation-heavy `lib/src/widgets/menu_fusion.dart`.

`DartPerformanceMode.latency` is documented as trading throughput/memory for latency and not suitable indefinitely (`E/lib/ui/platform_dispatcher.dart:3146`). The direct dispatcher setter forwards into `Dart_SetPerformanceMode` (`platform_dispatcher.dart:851`; `E/lib/ui/window/platform_configuration.cc:680`). However, in this pinned framework, `SchedulerBinding.requestPerformanceMode` only records/refcounts the requested mode; the examined body has no forwarding call when entering it (`F/src/scheduler/binding.dart:1287`). Disposal does forward balanced (`:1309`). Do not assume the scheduler handle alone activates VM latency mode in 3.47.2.

This is an investigation finding, not a recommendation for every MorphClock to set a global mode. The VM implementation/effect is not available here, and independent package users can conflict. If GC-tail profiling justifies a trial, coordinate one host-owned short interaction scope and verify the actual VM mode and memory cost. Existing allocation fixes remain more concrete.

**Ranked plan**

1. **Qualify the weak-device paths and measure the actual limiting stage.** Extend the existing passport, not the production code in this audit: A12/A14-class Metal, one weak Vulkan device and one real Impeller GLES fallback. Record backend, actual cadence, target dimensions/formats, warm/cold state, allocated/uploaded bytes and GPU time. Run a tiny complete liquid capability render; do not trust the uncompressed-format getter. Include settled idle, held static input, small unrelated animation, scroll behind resting glass, and changing fused menu. Existing iPhone 16 Pro numbers cannot rank these targets.
2. **Audit rectangular bounds and Metal damage first (4–7).** Highest plausible steady-state weak-GPU payoff with limited architectural change. Preserve the complete sampling halo; compare small damage and full-scroll workloads. Reject edge artifacts or damage omissions. Do not switch to bounded blur merely because it has a `bounds` parameter.
3. **Make first-use warm-up concrete (12).** Extend existing precache with a minimal actually executed pipeline/texture-use matrix. Prioritize Vulkan/GLES first-interaction tails; match final-filter variants and target configuration. Report startup cost separately, and verify fresh-cache and repeat-launch behavior.
4. **Implement composited-property update classification (1–3).** Reuse the proposed render-object-host work, but explicitly use `markNeedsCompositedLayerUpdate` where it applies. Measure avoided builds/paints and retained scene submissions. Then consider relaxing tracker `alwaysNeedsAddToScene`, preserving pre-scene invalidation and the GPU submission guarantee.
5. **Batch changing-field uploads and cap retained capacity (13, 23).** Preserve today's unchanged-sample reuse; use subregion copies and staging retention where several updates justify them. Add byte budgets/memory-pressure response. Measure upload command count, CPU encode time, and peak memory without sacrificing idle sleep.
6. **Trial RGBA16F fields before globally lowering matte resolution (9, 8).** Smaller scope and an explicit byte-saving hypothesis. Include packing cost and actual GLES usage tests. Then try a reduced optical-data grid with full-quality coverage. Require motion films, not only static screenshots; make any accepted tradeoff explicit.
7. **Try selective reduced arithmetic precision only after compiler-output inspection (10).** Keep coordinate and matte codec math high precision. No default `mediump` conversion and no unsupported cross-backend half promise. Stop if emitted code or GPU timing shows no benefit.
8. **Use bounded instancing/dirty atlas updates only if density measurements demand it (14–17).** Preserve the earlier explicit-container/paint-order contract. The GLES emulation path and area cost are kill criteria. Do not combine render passes on this engine just to lower command-buffer count.
9. **Consider static-output caching only for a host-declared immutable backdrop (11).** Potentially large Android savings while unrelated content animates, but high integration risk and redundant with Metal damage in some scenes. No automatic screenshot-per-frame bridge.
10. **Keep GPU fusion, live worker-isolate tracing and VM directives as evidence-gated research (18–20, 24).** Pursue only after a weak-device profile shows a remaining CPU bottleneck large enough to justify the representation/deadline cost. The sources do not establish portable compute dispatch, a safe unchecked-loop switch, or an effective scheduler latency-mode shortcut.

For every experiment, compare one change at a time against the current renderer under the same scene/tier/cadence, include GPU durations and first-use outliers, and preserve the native reference films and replay tests. A reduction in Dart layers, render passes, or allocated texels is useful evidence of removed work; acceptance is sustained weak-device latency/energy improvement with the same intended glass and motion.
