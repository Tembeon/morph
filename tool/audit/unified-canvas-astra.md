**Independent assessment: unified glass canvas — 2026-10-05**

**Recommendation: prototype a bounded, explicit glass compositor; do not pursue “unlimited elements are nearly free” or mandate one pass each for body/chrome/overlays.** Batching compatible peer surfaces can amortize filter setup, geometry submissions, texture allocation, and possibly blur work. It cannot eliminate work proportional to visible pixels, changing geometry, material diversity, or sequential optical dependencies. Three semantic screen categories are useful API scopes, but they are not necessarily three valid rendering passes. The correct unit is a set of surfaces that can read the same completed backdrop at the same position in composition order.

This is a source-based assessment, not a new device benchmark. I inspected the working tree at HEAD `c4a79a02c57eb9ef983a5a8946c3d4c1667fbdf3`, the requested passports/research, and the installed Flutter 3.47.2 SDK (engine `a804b261645ef8c13eb3d5c44a5c2fb0340c5539`). There were pre-existing unrelated working-tree changes, and other work changed documentation concurrently. The final check incorporates the newly documented owner decision to use explicit BackdropGroup sections; source lines reflect that check. Only this report was written by this audit. Repository references below are `file:line`; SDK references explicitly identify local SDK sources. Proposed thresholds are engineering acceptance criteria, not measured UIKit constants.

**The premise needs two corrections before estimating savings.**

First, ordinary glass already uses GPU analytic geometry. A `LiquidGlassLayer` packs primitives, evaluates their SDF in a Flutter GPU pass, then feeds a matte to the final backdrop shader. It can already contain multiple shapes. The widget host creates one layer for separate body surfaces, another for each fused body, and independent layers for lifted surfaces; “one pass per control” is only an approximation. See `lib/src/widgets/glass_liquid_native.dart:220`, `:381`, `:388`, `:438`; `lib/src/glass/renderer/internal/flutter_gpu_geometry_renderer_native.dart:401`; `lib/src/glass/renderer/shaders/gpu/geometry_fragment.glsl:48`.

Second, CPU-traced fields are principally for actual fusion, not every control. Spacing-zero unions now carry exact rounded boxes and a path, without a sampled field. Nonzero container fusion still samples/traces a field; menus use a Gaussian-blurred union with optical-normal and thickness data. Analytic shapes therefore do not offer a blanket replacement for today's CPU work. See `lib/src/widgets/glass_outline.dart:671`, `:694`, `:772`; `lib/src/widgets/menu_fusion.dart:62`; `lib/src/widgets/glass_liquid_native.dart:287`.

The research note is valuable but partly historical. Sample-buffer identity already avoids repeated uploads (`lib/src/glass/renderer/internal/flutter_gpu_geometry_renderer_native.dart:1024`); container outlines already reuse common translations (`lib/src/widgets/glass_outline.dart:679`); shader settings use lazy synchronization (`lib/src/glass/renderer/rendering/liquid_glass_layer.dart:510`); the passport records removal of per-surface shadow saveLayers (`tool/ios_reference/spec/glass-renderer.md:127`). Do not count these as future unified-canvas wins. Conversely, the 16-shape limit remains real: Dart stops packing at 16, the geometry/material shaders define `MAX_SHAPES 16`, and material IDs are encoded against that limit. Simply placing a screen under the existing layer would lose shapes. See `lib/src/glass/renderer/rendering/liquid_glass_layer.dart:1446`; `lib/src/glass/renderer/shaders/gpu/geometry_fragment.glsl:13`; `lib/src/glass/renderer/shaders/gpu/material_gradient_fragment.glsl:99`.

**Cost model: count pixels, updates, and dependencies as well as elements.**

Let `N` be visible participating surfaces; `L` current glass render layers; `G` valid backdrop-capture groups; `D` layers whose geometry changes this frame; `P_i` physical pixels in layer i's padded filter rectangle; `F_i` field-grid nodes; `n_i` primitives in layer i; and `K` the number of required sequential backdrop stages. Let `R` be the sum of rectangles processed by the proposed compositor, and `k(p)` the number of spatially relevant primitives at pixel p. `R` can greatly exceed the covered glass area: a navigation bar plus a bottom toolbar has an almost screen-sized bounding rectangle.

Conceptually, today's costs are:

```text
UI/encoding ≈ widget/layout/paint work(N)
            + Σ changed fused bodies trace_and_sample(F_i, n_i, blur kernel)
            + Σ D transform/pack/submit(n_i)
            + retained transform/clip checks + changed-content recording

GPU ≈ Σ G capture_cost(source extent, format, pass state)
    + Σ L [filter setup + blur_i(P_i and sampling halo) + shade_i(P_i)]
    + Σ D [geometry_i(P_i, n_i) + optional material_i(P_i / 64, n_i)]
    + shadows + content replay + ordinary Flutter composition
```

These are accounting terms, not additive frame latency: UI, raster, and GPU pipelines overlap. A backdrop “readback” in the repo means a GPU capture/resolve/snapshot, not necessarily a GPU-to-CPU read. Capture cost and actual blur reuse must be measured in Impeller: a shared key can reuse inputs and eligible filtering, but differing per-layer shader filters still need their own output work. The current final filter explicitly composes blur with the shader (`lib/src/glass/renderer/rendering/liquid_glass_layer.dart:1162`); mixed appearance maps are downsampled eightfold on each axis (`lib/src/glass/renderer/internal/flutter_gpu_geometry_renderer_native.dart:247`, `:326`).

Geometry is retained when unchanged, including shared translation, so `D` can be zero while moving content behind glass still requires backdrop shading. This favors cached mattes over evaluating analytic geometry every frame for static chrome. See `lib/src/glass/renderer/internal/flutter_gpu_geometry_renderer_native.dart:15`; `lib/src/glass/renderer/rendering/liquid_glass_layer.dart:887`, `:1262`.

| Design | Geometry work | Remaining cost and likely behavior |
|---|---|---|
| Current bounded layers | Roughly sum of changed local areas × local primitive work; CPU fields only where fusion requires them | `G` captures, `L` filter outputs, good local retention; per-layer setup can dominate many tiny surfaces. |
| One shader looping over every primitive | `O(R × N)` each shaded frame, even when shapes rest | Fewer submissions, potentially far more ALU and empty-space work; large loops/register pressure are a poor scaling strategy. Bounds tests reduce expensive SDF evaluations but still scan N bounds. |
| Unified precomputed field/matte | Final geometry lookup `O(R)`; generation may still be `O(R × N)` or CPU `O(F × N)` | Adds field storage/write/read traffic. Building the whole field when one item moves discards today's local reuse. |
| Spatially culled analytic shader | Binning approximately `O(N + shape–tile references)`; pixel work `O(Σ k(p))` | Near area-bound only while local density stays bounded. Tile overflow, giant shapes and heavy overlaps still scale with N. |
| Bounded quads/instances into a shared matte or atlas | Approximately `O(N + sum of covered quad pixels)` for independent primitives | Efficient GPU raster culling; fusion and overlap ownership require additional handling. One render pass can contain many draws. |

All unified variants still pay `K` backdrop stages, blur/optics, labels, hit-testing state and material updates. Since compatible controls already share a capture, batching those controls may save **zero captures**. Its initial upside is fewer filter outputs, geometry encoders, and layer objects. To remove CPU tracing as well is a separate geometry-contract project.

“Nearly free extra elements” is defensible only narrowly: fixed total covered area, bounded local overlap, one compatible material/backdrop stage, small descriptor updates, and spatial culling. At fixed element size, area rises with N; at fixed screen area, subdivision increases boundary pixels, antialiasing, descriptor traffic and content. With full-screen `1206 × 2622` coverage, an uncullled 100-shape loop implies about 316 million candidate checks per frame before optics. That arithmetic is illustrative, not a timing prediction. A smaller pass count can therefore be slower.

**Paint order is the main feasibility boundary.**

The repo's grouping warning is an observed correctness constraint, not a theoretical objection: on its Metal engine, later group members can see the resolve texture at the last backdrop flip, missing intervening painting. The resting-body repro still differs by 72 liquid / 43 frosted channel levels; moving the scroll-edge effect into the chrome group visibly removed the fade from the capsules. See `CLAUDE.md:195`; `tool/ios_reference/spec/glass-renderer.md:225`, `:301`, `:342`. The owner has now selected explicit per-section BackdropGroups (option C), rather than automatic detection (`tool/ios_reference/spec/glass-renderer.md:329`); the bad repro describes unsectioned sharing, not an absence of a supported remedy. Flutter's public API also warns against sharing a key between overlapping filters. [Flutter BackdropFilter documentation](https://api.flutter.dev/flutter/widgets/BackdropFilter-class.html).

Consider original paint order `background → glass A → label A → stripe → glass B → label B`. Rendering both glasses at the end captures their labels/stripe as input and places glass over foreground text. Rendering both at A's position makes B miss the stripe. Painting all non-glass first, then all glass, then all labels is correct only under a new explicit container contract; it is not a transparent optimization of arbitrary Flutter trees. Even disjoint outlines need a sampling-reach check because refraction and blur fetch outside the silhouette (`lib/src/glass/renderer/rendering/liquid_glass_layer.dart:1331`).

A collector can safely combine surfaces when the common background is already complete, their output/content ordering is declared, and they do not require one another's filtered output. Treat dependencies as a graph: an edge exists when a later surface must sample earlier output or intervening content. Ordered stages follow that graph. Two glass planes can sit in “page body”; one “overlay” can contain a sheet surface, sheet content, a menu and a lifted lens, each with dependencies. `K` can approach N in a deliberately stacked scene.

| Concern | Required compositor behavior |
|---|---|
| Text and other foreground | Keep live content once in Flutter's normal retained tree, positioned above its own glass stage. Do not put labels into the common background or replay them twice. Text outside a lens remains ordinary text. Current seam explicitly supplies `content` above surfaces (`lib/src/widgets/glass.dart:288`, `:357`). |
| Glass over glass | Preserve separate capture/shade stages if upper glass refracts the already-shaded lower glass. A single minimum-distance field selects a boundary; it cannot encode two independent translucent planes or sequentially refracted images. Unioning them changes optics. |
| Lifted lens content | Preserve `body → clipped ordinary content → per-slot magnified copy → lens glass`. The copy is magnified around each content slot, with up to three growth strips, not one screen-centered scale. Current lens explicitly uses an independent layer (`lib/src/widgets/glass_liquid_native.dart:412`, `:423`, `:438`, `:604`). Multiple lenses may share a stage only when their complete optical inputs are independent. |
| Transforms | Store each surface's local-to-container matrix and inverse; transform normals/distances correctly under nonuniform scale, and preserve pixel snapping/DPR. Ancestor compositor-only movement must update descriptors without waiting for child paint. Current inverse basis and conservative distance scale are at `lib/src/glass/renderer/rendering/liquid_glass_layer.dart:1448`; retained motion handling is at `:1255`. Initially fall back for perspective, singular transforms and unsupported deformation. |
| Clips | Per-surface ancestor clip stacks are not equivalent to clipping the whole canvas. Preserve arbitrary paths, scroll clips, AA and sampling support, including clipping between a surface and its owner. A mask atlas can represent coverage but not automatically the same blur boundary conditions. Current code retains/synchronizes clips (`lib/src/glass/renderer/rendering/liquid_glass_render_object.dart:663`). |
| Opacity/blend modes | Surface visibility can be data. Group opacity over overlapping glass plus labels cannot generally be distributed into individual surface alphas: `opacity(composite(A,B))` differs from `composite(opacity(A),opacity(B))`. Retain isolation boundaries/fallbacks. The seam deliberately uses `MorphGlassSurface.opacity` (`lib/src/widgets/glass.dart:183`); the passport separately notes alpha-255 OpacityLayers are effectively free (`tool/ios_reference/spec/glass-renderer.md:409`). |
| Different materials and animation | Carry per-surface tint, visibility, gamma, lighting, optical center, displacement, shrink axis and material identity. Existing mixed appearance support does not make all settings per-surface: `_layer` takes settings from the first surface (`lib/src/widgets/glass_liquid_native.dart:223`). Varying blur radii require compatible batches, multiple blurred inputs, or a new variable-blur algorithm with its own fidelity/performance costs. |
| Hit testing and semantics | Keep control RenderObjects, listeners, focus, semantics, z-order and layout. The compositor replaces visual effects only; its output must not absorb pointer events. Visual fusion need not merge interaction regions. Current content copies deliberately use `IgnorePointer` and `ExcludeSemantics` (`lib/src/widgets/glass_liquid_native.dart:590`). |
| Platform views | Treat native views as an explicit unsupported/special path until validated. iOS uses hybrid composition with UIViews outside Flutter's ordinary texture stream; special platform-view blur support is not proof arbitrary refractive shader filters can sample them. Texture-backed video and native UIViews need separate tests. [Flutter iOS platform-view documentation](https://docs.flutter.dev/platform-integration/ios/platform-views). |

**Flutter GPU can make the data passes; it does not automatically own the Flutter backdrop.**

The current architecture is a sensible split: Flutter GPU renders geometry/material textures; a `dart:ui` shader filter obtains the compositor's current input. `ImageFilter.shader` requires the first sampler to be supplied by the engine as the filter input. A package can therefore implement one unified final filter for a valid group without a Flutter engine fork. It cannot assume the live Impeller scene target is available as a `gpu.Texture` inside an arbitrary custom GPU pass. See `lib/src/glass/renderer/rendering/liquid_glass_layer.dart:1165`, `:1195`; [ImageFilter.shader API](https://api.flutter.dev/flutter/dart-ui/ImageFilter/ImageFilter.shader.html).

The installed SDK does support instancing (`bin/cache/pkg/flutter_gpu/lib/src/render_pass.dart:648`), stencil state (`:577`), scissor (`:607`), and wrapping a GPU-backed `ui.Image` (`bin/cache/pkg/flutter_gpu/lib/src/texture.dart:89`), all under `/opt/homebrew/Caskroom/flutter/3.19.1/flutter/`. That old directory name does not identify the installed version: `bin/cache/flutter.version.json:2` says 3.47.2. `Texture.fromImage` wraps an image one already has; it does not obtain an in-progress scene backdrop. Its documentation explicitly warns that `toImageSync` may not yet have a GPU texture (`texture.dart:98`). A screenshot-per-frame bridge adds recording/rasterization, synchronization or stale-frame risks and should not be the production plan.

Do not equate a Flutter layer, a shader invocation, a draw, a render pass, a command buffer and a backdrop capture. A batched geometry pass can contain N draws and still amortize pass transitions. A “single” glass filter with Gaussian blur may require several backend passes. Current geometry and optional material passes deliberately use separate command buffers because this engine's pass lifecycle caused nested-encoder failures when sharing one (`lib/src/glass/renderer/internal/flutter_gpu_geometry_renderer_native.dart:488`). Their submission is already deferred/batched in time (`:528`, `:558`). Combining distinct passes into one command buffer is not a safe quick win; multiple draws within one actual pass are a different proposal.

Flutter GPU remains documented as preview/Impeller-dependent; design to the pinned SDK, not to every feature Metal hardware can support. Do not make compute shaders, storage-buffer/atomic workflows, tile shaders, indirect draws, or borrowing the engine's stencil attachment prerequisites without verifying exposed APIs and cross-backend behavior. Raster passes and CPU-built spatial lists are enough for the first experiment. [Flutter GPU engineering documentation](https://github.com/flutter/flutter/blob/master/docs/engine/impeller/Flutter-GPU.md).

**A paint-time collector must be retained, not rebuilt from callbacks that happen to run.** A repaint boundary may reuse its layer without repainting descendants. A list populated only by this frame's paint calls will omit static surfaces; collecting in widget build misses paint transforms and actual ordering. Keep mounted registrations with stable IDs, revisions, owner scope, transform/clip state and detach handling. Collect updated records during normal rendering, then finalize the complete set before retained-layer dirtiness and scene submission. The existing transform layer explicitly says `addToScene` is too late to update effects after retained rendering has been selected (`lib/src/glass/renderer/internal/transform_tracking_repaint_boundary_mixin.dart:140`).

An explicit parent can arrange background, effect, and foreground child layers and finalize its effect after collecting children. It cannot generally infer where arbitrary foreign pictures should be split into background/foreground. The passport already explains why PictureLayer bounds cannot reliably identify intervening relevant painting (`tool/ios_reference/spec/glass-renderer.md:307`). Avoid repainting/reparenting an arbitrary screen twice to discover order. Overlays also need their own compositor ownership even when they carry the source painter through inherited themes (`CLAUDE.md:178`).

**UIKit supports the container concept, not an unlimited-performance promise.** Apple documents `UIGlassContainerEffect` as combining nested glass effects into one view behind the container's content, with spacing controlling merging. That is exactly the explicit ordering contract that makes batching plausible. It does not document an analytic global SDF, a fixed number of Metal passes, or constant cost as N grows. [Apple UIGlassContainerEffect documentation](https://developer.apple.com/documentation/UIKit/UIGlassContainerEffect?changes=_8).

Apple's AppKit talk goes further and describes a shared sampling region and one sampling pass for a glass container. This is evidence for amortizing sampling; it is not proof UIKit uses the identical implementation or that all shading/geometry is one pass. [WWDC25: Build an AppKit app with the new design](https://developer.apple.com/videos/play/wwdc2025/310/?time=0). Morph's own measurement names `CASDFLayer`/`CASDFElementLayer` and a specific merge law (`tool/ios_reference/spec/skin-merge.md:8`); that is useful structural evidence, not a published GPU algorithm. Preserve the measured behavior instead of extrapolating hidden implementation details.

**Which alternatives are worth trying.**

| Alternative | Assessment |
|---|---|
| Analytic SDF directly in final shading | Good isolated experiment for one/few changing primitives: removes matte generation and a matte sample, but repeats SDF work whenever the backdrop updates. Resting cached geometry can be cheaper. Reuse existing shape/optics math; rounded superellipse solvers are not equivalent to a cheap circular rounded-box formula. Avoid a screen-wide N loop. The research already identifies upstream's former direct-render path (`tool/audit/perf-research-2026-10-05.md:605`). |
| Tile lists in final shader | Strong candidate for larger groups. Bin conservative support bounds into tiles; each pixel examines only its tile list and material records. Include AA/contour/fusion support and proper neighborhood halos. Preserve original fusion evaluation order and bounds; smoothing is not automatically associative or bounded by one primitive's local box. Never truncate overflowing tile lists: split/fallback. Store descriptors/lists in formats the runtime shader can sample exactly. |
| GPU field texture | Useful for expensive changing fusion if the field's generation moves to GPU too. Merely concatenating today's CPU fields into one texture saves no tracing. Preserve distance, optical normals, half-thickness and material ownership; one scalar SDF is insufficient. A Gaussian-blurred menu field likely needs several passes or repeated neighborhood evaluation. Its CPU path is also used for clipping/shadows/fallbacks, so removing it requires a coherent replacement, not synchronous GPU readback. |
| Per-layer compositor with retained local geometry atlas | Best general architecture experiment. Keep each body's authoritative shape/field and local invalidation, pack reusable geometry into a shared atlas, and use one final filter per compatible stage/material bucket. It avoids tracing a screen-sized union. Atlas assembly and lookup are additional costs; direct writing to atlas regions or cached indirection can be compared later. |
| Instanced bounded quads | Particularly good for independent primitives in a geometry/ownership pass. GPU rasterization restricts work to each quad instead of testing every shape at every pixel. Retain exact ordering/ownership; default overwrite or alpha blending is not SDF union. At overlaps, separate staged glass from true fused bodies. Instancing final refraction still needs an accessible backdrop, which the runtime filter supplies more naturally than a free-standing GPU pass. |
| Stencil/coverage masks | Helpful to reject empty pixels in a GPU pass; stencil alone provides neither distance/normal nor blur/refraction. It costs mask draws and depth/stencil storage. A mask in a custom Flutter GPU target does not become the engine filter's stencil. A sampled mask early-out is feasible but still invokes the filter across its rectangle. Compare with simpler disjoint rectangles/tiles first. |
| Several small compositor batches sharing a backdrop key | Often better than a single full-screen rectangle. Top and bottom chrome can share a valid capture while retaining bounded shading regions. This deliberately trades a few draws/filter outputs for lower fill and blur cost. Measure actual engine reuse because the shaders differ. |

The current “outline is truth” contract must survive any of these: callers own fusion; the renderer shades the supplied result (`CLAUDE.md:225`; `lib/src/widgets/glass.dart:319`). Representing that result as an immutable analytic/field descriptor is a possible future seam extension. Having a global renderer independently re-fuse every nearby control would change semantics. Smooth container fusion, ordinary union and Gaussian menu fusion are three different operations; substituting one for another loses fidelity (`lib/src/widgets/glass_outline.dart:658`; `lib/src/widgets/menu_fusion.dart:62`; `tool/ios_reference/spec/skin-merge.md:30`).

**Memory, invalidation and warm-up can reverse the expected win.**

A full-screen `1206 × 2622` texture is about 12.65 MB at 4 bytes/pixel, 25.30 MB at 8, or 50.59 MB at 16 (decimal MB; illustrative DPR-3 dimensions from the phone's documented 402 × 874 pt size, `tool/ios_reference/spec/README.md:25`). Three full-screen RGBA32F fields alone are about 152 MB; three retained versions of each would be about 455 MB, before backgrounds, blur intermediates, mattes and content. This is an intentionally bad allocation model, not a forecast. Current CPU fields are coarse logical grids, not full-resolution screen buffers; sample storage is four floats per node (`lib/src/glass/renderer/glass_field.dart:14`). Prefer bounded/atlas allocation, measured precision and byte accounting.

A 25.30 MB surface read plus write at 120 Hz is roughly 6.1 GB/s of nominal traffic. Real tile memory, resolves, compression, caches and pass fusion change external-memory traffic; do not report this arithmetic as measured bandwidth. It explains why replacing several small filters with a full-screen field/blur can regress despite fewer passes.

Keep geometry, appearance, clip, transform and background invalidation separate. If one thumb moves, redraw its old and new atlas/tile regions plus support, including exposed underlying contributors; do not regenerate all static chrome. Conversely, a scrolling background invalidates final shading even with unchanged geometry. Dirty regions are unsafe unless cleared/restored correctly, and ring-buffered targets must contain valid unchanged tiles on every version. Current rings deliberately retain in-flight resources (`lib/src/glass/renderer/internal/flutter_gpu_geometry_renderer_native.dart:570`, `:893`); a larger shared ring magnifies both lifetime mistakes and memory peaks.

Precision changes can shift zero contours, optical corner normals, thin necks and colored glints. The current field explicitly stores a turned gradient and thickness, and the matte packs 12-bit codes requiring high precision (`lib/src/glass/renderer/shaders/gpu/geometry_field_fragment.glsl:1`, `:12`). Material ownership is already approximate/two-contributor (`lib/src/glass/renderer/shaders/gpu/material_sdf.glsl:3`) and its coarse filtered map should not silently become a general screen-wide ID buffer; sharp IDs need stable nearest lookup or an explicit boundary treatment.

Limit shader variants. A giant N limit may increase code/register pressure; permutations for material × clips × optics × shape type can increase load/pipeline warm-up and memory. Existing assets and `precache()` are a useful foundation, but a cold-start test must verify first appearance, actual GPU pipeline creation and native packaging (`lib/src/widgets/glass_liquid_native.dart:54`; `CLAUDE.md:235`). Do not hide first-use costs inside an averaged outline microbenchmark; the passport already caught roughly 45 ms of one-time work contaminating a warm measurement (`tool/ios_reference/spec/glass-renderer.md:385`).

**Prototype in two separable experiments before changing public architecture.**

1. **Prove batching with today's authoritative geometry.** Add an experimental explicit container in a future implementation branch: completed background, registered peer surfaces, foreground content. Start with nonoverlapping ordinary buttons in one compact region, identical optical settings/blur, and tint as either uniform or existing supported appearance data. Keep N ≤ 16 initially. A/B current layers versus one existing-style `LiquidGlassLayer` while preserving all shape math. This establishes the maximum practical gain from removing layer/filter setup without conflating it with a new SDF algorithm. Include sparse top/bottom chrome immediately to expose bounding-area regressions.

2. **Prove scalable geometry independently.** Extend that controlled container to 32/64/128 surfaces with bounded quad/instance geometry or tile-indexed descriptors. Do not merely increase `MAX_SHAPES`; redesign material IDs and descriptor lookup. Compare a retained geometry atlas with a direct analytic final filter. Measure static shapes over animated background and one moving surface among many static ones, not just all surfaces moving together. Keep fusion fields on the existing path until batching itself earns its cost.

3. **Then integrate a retained collector.** Stable registrations contain shape/outline revision, transform/clip chain, material/optics, paint-order token, background-stage ID, content association and support bounds. Updating motion marks effect paint/data dirty without rebuilding all surface widgets; ordinary control trees stay mounted. Finalize records before composition, preserving the retained-motion hooks. Explicitly split at backdrop dependencies, opacity isolation, unsupported clips/transforms, incompatible blur, nested glass and platform views. Preserve a cheap fallback and no work for an empty group. This is an extension of the current seam, not an implicit change to every `MorphGlassLayer` (`lib/src/widgets/glass.dart:470`).

4. **Only after that, investigate GPU fusion.** Keep the exact measured merge law and Gaussian menu algorithm. Determine whether CPU paths still needed for shadows, clips or non-GPU tiers dominate; do not claim their cost disappeared because the optical field is GPU-generated. A field atlas may be sufficient without replacing tracing. No screen-wide field is required for a unified final filter.

For the first production candidate I would favor compact chrome/container batches and a retained geometry atlas, with a separate lens stage. I would keep widely separated regions separate if area costs beat setup savings. Do not start by migrating the whole page or menu fusion: today's measured scenes already fit comfortably within the 8.33 ms 120 Hz budget, and the latest shadow change produced measurable gains with far less architecture risk (`CLAUDE.md:1133`; `tool/ios_reference/spec/glass-renderer.md:137`).

**How to measure on the iPhone 16 Pro.**

The existing passport provides the base protocol: locked phone, fixed source checkout, profile app, five timed repeats, active-frame percentiles, and screenshots outside timed windows (`CLAUDE.md:1104`; `tool/ios_reference/perf/audit.sh:4`). This read-only audit did not run it. For the later prototype:

1. Record source commit plus any patch hash, Flutter/engine revision, iOS version, actual render-target dimensions/formats, tier, thermal state and observed display cadence. Use the lock protocol at `tool/ios_reference/spec/README.md:72`; disable tier adaptation and hold liquid. Check actual 120 Hz presentation rather than assuming it from a setting. Alternate baseline/prototype order across launches, cool between runs and keep brightness/power conditions comparable. Run the existing six audit scenes first, then repeat shortlisted results in release.

2. Add a scaling matrix: N = 1, 4, 16, 32, 64, 128; fixed element size until viewport saturation and fixed total coverage as separate experiments. Test compact vs sparse layout, static vs scrolling background, none/one/all shapes moving, uniform vs heterogeneous tints, same vs differing blur, overlapping/fusing vs independent surfaces. Use representative labels and shadows plus a geometry-only variant. Report visible N and tile occupancy, not the number mounted offscreen.

3. Record UI/build, raster, p50/p95/p99/worst, missed presentation deadlines, `vsyncOverhead`/`totalSpan`, and actual GPU durations. Do not add build and raster p95 or equate rasterDuration with GPU execution. Use Instruments Metal System Trace/GPU capture to inspect encoders, captures/resolves, blur and final filters, attachment load/store traffic, stalls and texture allocations. Verify tool names/options for the installed Xcode; the existing research outlines this workflow at `tool/audit/perf-research-2026-10-05.md:790`.

4. Add low-overhead profile instrumentation for capture groups, actual GPU passes/draws/submissions, filtered pixel rectangles, atlas bytes, uploaded bytes, tile-list occupancy/overflow, dirty geometry area, tracing time, collector time and content-copy fallback counts. Several existing renderer counters are assert/debug-only; expose benchmark counters deliberately instead of reading zeros in profile. Widget tests do not run Impeller and cannot establish real GPU pass count (`CLAUDE.md:1113`). Counts diagnose cost; measured GPU time and presentation determine success.

5. Run fidelity films/shots in light and dark at matched motion times: colored stripes painted between body controls; scrolling through both bars/edge fades; lifted segmented/tab labels moving across slot boundaries; menu fusion/tail/submenu; sheet with glass inside; nested overlays; rotation/nonuniform scale/scroll clips/group fades; rapid mount/unmount and N > 16. Include native platform views as a separate capability test. Preserve hit testing, semantics and reparenting behavior. Use native reference films as well as baseline Flutter, because the current resting-body group repro is already wrong. Pixel diffs need a repeated-baseline noise envelope and regional/temporal inspection, not only a whole-screen average.

6. Test cold first use, settled idle for five seconds, and a sustained several-minute scroll/interaction loop for thermal behavior and resident memory. Require no self-scheduled idle frames. A 20-second warm synthetic run cannot establish energy or thermal improvement. Attribute savings separately to grouping, direct geometry, fusion, widget rebuilds and blur rather than changing all simultaneously.

**Acceptance and kill criteria, set before implementation.**

These proposed gates aim to prevent an attractive pass-count reduction from becoming a costly rewrite:

| Gate | Continue / reject |
|---|---|
| Correctness | Reject a general replacement if it needs stale-frame snapshots, moves text through glass, loses shapes beyond a cap, changes measured fusion/optics, or crosses a dependency boundary to achieve its savings. Unsupported cases may explicitly fall back; common cases must remain correct. |
| Realistic benefit | Continue integration only if repeated on-device results beat the noise envelope and yield approximately ≥15% **and** ≥0.3 ms improvement in GPU time or the limiting UI/raster stage in at least two representative intended workloads. My expected result is a useful but bounded improvement for many compatible surfaces, especially where repeated filter/encoding setup is measurable. The strongest architecture is **explicit composition stages, spatially bounded work, and retained per-surface geometry**, potentially with one final shading filter for each compatible batch. The owner should fund that experiment, not a promise that one canvas makes arbitrary amounts of glass free.
