# P2: разрешение закрытия меню

База `9fcf9d19`, 2026-10-16. Это протокол сокращённого P2, не публичный API пакета. P2 остаётся открыт.

## Сценарий вызова

Приложение использует SDK `PopScope` и `Navigator.pop`. Асинхронная граница проверяется через существующий deprecated `WillPopScope`, без нового callback в API morph. Обычный синхронный жест должен совпадать с прежним replay; ожидающее разрешение оставляет меню открытым и работающим.

```dart
ProbeMenuSource(
  pointerInput: true,
  menuBuilder: (_) => PopScope<void>(
    canPop: canDismiss,
    child: menu,
  ),
)
```

Внутренний поток: измеренный запрос → допуск без вызова приложения → доставка после команды/advance → SDK permission → текущий шаг владельца → SDK pop → движение только после успешного `didPop`. Внутренняя история SDK может поглотить pop и оставить меню открытым.

## Состояние и границы

Route владеет единственным ожидающим запросом: identity, `requestedAt` и общим Future проверки SDK permission. Повторный ввод и SDK `maybePop` разделяют эту проверку. Приложение не вызывается из admission во время интегрирования. Синхронные решения не переходят через Future и сохраняют исходный deadline.

```dart
bool _admitMotionClose(double requestedAt);
void _drainDismissal();
Future<RoutePopDisposition> willPop();
void _consumeApprovedDismissal();
bool _isLive(_DismissAttempt attempt);
void _invalidateDismissal();
```

До вызова guard и после ожидания проверяются identity, активный route, currentness, владение lease и отсутствие closing/dispose. `PopScope` и внутренняя история читаются повторно. Замена, удаление, временное cover/uncover, отдача модели и программный pop отменяют ожидающий запрос. Исчезновение одного source сохраняет разрешение живого route: он уже умеет закрываться без посадки в источник. Ошибка guard не является разрешением; она сообщается через `FlutterError`, запрос очищается, повторная попытка разрешена. Отмена разрешает внутренний Future отказом, но не может отменить произвольный Future приложения; его поздний результат не применяется.

При реализации убран отдельный числовой navigation epoch: каждая смена навигационного окружения очищает pending identity, старый объект никогда не используется повторно. Identity уже является поколением операции; счётчик дублировал ту же проверку. Cover/uncover и повторный вход проверяются настоящим Navigator. Это упрощение реализации относительно обоих кандидатов, без изменения правила отмены.

Проверка реализации выявила ещё одну границу. Нельзя отдавать нескольким `maybePop` один успешный ответ без одноразового допуска: первый SDK pop может снять внутреннюю историю, а второй — сам route. Теперь общим остаётся Future проверки guard, а каждый вызывающий `willPop` после await повторно проверяет identity и может ровно один раз занять допуск к pop. Остальные получают отказ. Если SDK выигрывает, `didPop` отменяет отложенную работу модели; если внутренний запрос выигрывает допуск, единственный pop выполняется на шаге владельца. Исходный провал сохранён.

Уже выданный SDK ответ `pop` не отзывается задним числом. После его выдачи остаются обычные проверки `Navigator.maybePop` по текущему route entry и policy. Более сильная атомарность между выдачей ответа и SDK commit, включая мгновенный cover/uncover в этом интервале, здесь не обещается. Прямой запрос `willPop` без последующего Navigator-потребления не является проверенным API прототипа.

При одобрении запроса от модели route пробуждает существующие часы через `resumeAt(now())`. Следующий шаг владельца сначала продвигает модель, затем, до публикации, проверяет запрос и выполняет pop. Если SDK `maybePop` успел выполнить успешный pop раньше, он закрывает из текущего состояния владельца и отменяет отложенную работу. Программный pop сохраняет SDK-семантику и обходит veto. Он также отменяет ожидающий запрос, даже когда pop поглощён внутренней историей.

## Время

`requestedAt` — время первого запроса операции: измеренный deadline для model-first и текущий сэмпл для SDK-first. Для синхронного допуска `closeStartedAt == requestedAt`. Для настоящего ожидания время запроса остаётся provenance; закрытие начинается из текущего состояния при принятии решения владельцем. `closeStartedAt` не предшествует последнему сэмплу модели. Оно не получается прибавлением wall-clock ожидания к замершему времени модели.

Это уточнение прежней фразы «сохранить исходное время после разрешения». Уже проинтегрированные kicks не перематываются: контрпример с `advance(2); close(1)` даёт иную геометрию, даже если analytic progress совпадает. Замораживание меню на время произвольного Future и копирование/откат модели отклонены. В покое каноническое время по-прежнему приостанавливается; политика часов не меняется ради permission.

## Выбор формы

Два независимых кандидата и свежий judge работали на одной унаследованной модели; это не согласие разных моделей. Кандидат A хранит транзакцию в route с существующим bool admission. Кандидат B предлагает уступку управления на deadline, effect/drain/resolve и продолжение того же шага timeline. B лучше описывает будущую типизированную границу, но требует раннего переноса единицы 2.4. Для доказательства async SDK выбран A, с политикой существующих часов и завершением на шаге владельца из B. Оценки judge по пяти критериям: A 13/15, B 11/15; это сравнение проектов, не доказательство кода.

У A отклонён новый clock API с непрерывным временем сна. У обоих отложен обязательный first-build barrier: это более сильная семантика, чем обнаружение уже зарегистрированной SDK policy. Политика смонтированного содержимого обязательна; запрос до первого mount остаётся отдельным открытым решением. Внутренний admission в `lib/` не расширяется; будущая единица 2.4 обязана заменить его настоящей границей событий **до** финального сэмпла. Простое чтение очереди после полного advance и обратная команда со старым временем неэквивалентны.
